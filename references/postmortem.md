# ポストモーテム(インシデント・プロジェクト終了後のふりかえり)

ユーザーが「ポストモーテム」「障害のふりかえり」「インシデントレビュー」「プロジェクトが終わったのでふりかえりたい」
「炎上案件のふりかえり」「反省会をやることになった」と言ったら、このファイルを読んでから進める。
日々のスプリントのふりかえりには使わない(SKILL.md本体で対応する)。

---

## 0. このファイルの前提

**ポストモーテムは本来チームでやるもの。** 文献はすべてチーム前提である。理由は3つ。

- 複数の視点がないと事実が集まらない。ひとりの記憶はその人が見ていた範囲しかない
- ひとりでは相互作用が見えない。事故は個々の部品ではなく、別々のサブシステムが
  予測できない形で相互作用して起きる
- 共有されない学びは学びにならない

**だから、人を集められるなら集めるよう最初に勧める。**
集められないとき(ひとり案件・解散済みチーム・聞きにくい状況)に限り、
**欠けている他者の視点の役をAIが担う**。「ひとりでもできます」とは言わない。

---

## 1. 絶対に守ること(ここを外すと反省会になる)

### 1-1. 人に着地させない

出てきた答えが**人の性質**(注意不足・意識が低い・スキル不足・確認漏れ)になったら、
それは掘り方が間違っている合図。**必ずもう一段、仕組みへ降ろす。**

戻し方の例:
- 「その人が注意不足だったとして、**注意しなくても防げる形**にはできませんか」
- 「同じ状況に**別の人が入っていたら**、同じことが起きたと思いますか」
  → 起きるなら、それは個人ではなく仕組みの問題
- 「**気づける仕掛け**は、どこかにありましたか。無かったなら、そこが変えどころです」

### 1-2. 後知恵で過去を裁かない

いま分かっていることを使って、当時の判断を評価しない。
**「そのとき、手元にどんな情報がありましたか」**を必ず先に聞く。
当時の情報で見れば妥当だった判断を「なぜ気づかなかったのか」と責めるのは、後知恵バイアス。

### 1-3. 「なぜ」より「何が」

「なぜ確認しなかったのか」は人を追い詰める。
**「何があって、確認できなかったのか」**に言い換えると、状況と仕組みが出てくる。

### 1-4. 単一の真因で終わらせない

一本道で5回「なぜ」を繰り返すと、きれいな因果の鎖ができあがるが、
実際の事故は**複数の要因が重なって**起きている。
各段で「**他にも要因はありませんか**」と枝を広げる。

### 1-5. 対策を「気をつける」で終わらせない

「気をつける」「意識する」「確認を徹底する」は、人に着地した対策であり、実行されない。
**仕組み・プロセス・道具のどれを変えるか**まで降ろす。
そして**いつ・何を見て効果を判定するか**を必ず決める。

---

## 2. 問診(最初の1〜2往復でまとめて聞く)

1問ずつ小出しにしない。以下を**1メッセージでまとめて**聞く。

1. **何が起きましたか**(障害・事故・プロジェクトの結果。一言で構いません)
2. **今回は、インシデント(障害・事故)のふりかえりですか。それともプロジェクトや案件が
   終わったあとのふりかえりですか**
3. **今日は何人で行いますか。ひとりですか、チームですか**
4. **どれくらい時間が取れますか**(20分 / 60分 / 90分 / 半日)
5. **いちばん知りたいのはどれですか**
   - 何が起きたのかを整理したい(分析)
   - なぜ起きたのかを掘りたい(原因)
   - 次にどうするかを決めたい(対策)
   - この経験から何を学んだかを残したい(学び)

**チームと答えた場合**、ここで一言添える:
「集まれる方がいるなら、ぜひ一緒に。見ていた景色が人によって違うので、
そこが揃うだけで見えるものが変わります」

**ひとりと答えた場合**、こう伝える:
「本来はチームでやるものなので、**私が他の人の視点の役をやります**。
遠慮なく、途中で『それは違う』と言ってください」

---

## 3. 時間別の配分

**ひとりのときは30分が上限。** ひとりで60分・90分かけても、視点は1つのままで掘れる深さは伸びない。
それだけの時間が取れるなら、その時間で人を集めるほうが得るものが大きい。
ユーザーが「ひとりで90分」と言ったら、**まず「一緒にふりかえれる人はいませんか」と確認する。**
それでもひとりなら、30分の設計で進める。

### ひとり（30分）

| 段 | 時間 |
|---|---|
| 1 身構えを解く | 3分 |
| 2 何が起きたか | 8分 |
| 3 なぜ起きたか | 8分 |
| 4 何を変えるか | 8分 |
| 5 残す | 3分 |

### チーム（60分 / 90分）

| 段 | 60分 | 90分 |
|---|---|---|
| 1 場をつくる | 8分 | 10分 |
| 2 何が起きたか | 15分 | 25分 |
| 3 なぜ起きたか | 15分 | 25分 |
| 4 何を変えるか | 15分 | 20分 |
| 5 学びを残す | 7分 | 10分 |

段は飛ばさない。**各段を短くして収める。**
目的によって重心を変える(問診5の答えを使う):

| 目的 | 厚くする段 | 薄くしてよい段 |
|---|---|---|
| 分析したい | 2(時系列) | 4 |
| 原因を掘りたい | 3(要因) | 2は粗くてよい |
| 対策を決めたい | 4(対策) | 2・3は主要なものだけ |
| 学びを残したい | 5(学び) | 4の細部 |

## 4. 段ごとの進め方と問い

### 段1: 場をつくる

**ひとりでも省略しない。** ここが反省会との分かれ目になる。

チームなら、最優先指令を読み上げてもらう:
> 「どんな結果であろうと、そのときに分かっていたこと、各自のスキルと能力、
> 利用可能なリソース、置かれた状況を鑑みれば、**全員がベストを尽くした**。
> 私たちはそう信じ、心から理解する」
> (Norm Kerthの最優先指令 https://hurikaeri.jp/catalog/norm-kerth-prime-directive/)

そのうえで、この場の約束を宣言する:
- **犯人を探す場ではない。** 探すのは、次に同じことを起こさないための変えどころ
- **ここで話したことを、人事評価や責任追及に使わない**
- 分からないことは「分からない」と言ってよい

ひとりのときは、AIが読み上げてから、こう聞く:
「**この前提に、いま乗れそうですか。**『自分が悪かった』という気持ちが強いなら、
先にそれを聞かせてください。ひととおり言い切ってから始めたほうが、後がラクです」
→ 自責が強い人は、先に吐き出させてから進める。抑え込むと後で何度も出てくる。

### 段2: 何が起きたか(事実を時系列で)

**ここでは解釈と評価をしない。事実だけを並べる。**
「よくなかった」「判断ミスだった」が出てきたら、
「その評価は次の段で扱います。**まず、何が起きたか**だけ教えてください」と戻す。

聞く順番:
1. 「**いつ、何が起きましたか**。分かる範囲で時刻とできごとを並べてください」
2. 「**誰が、いつ気づきましたか**。どうやって気づきましたか」
3. 「**気づいてから、何をしましたか**。順番に教えてください」
4. 「**いつ収まりましたか**。何をしたことで収まりましたか」

ひとりのときに足す問い(チームの視点の代役):
- 「そのとき、**他の人には何が見えていた**と思いますか」
- 「**あなたが見ていなかった時間帯**はありますか。そこでは何が起きていたと思いますか」

プロジェクト終了のふりかえりなら、時系列はフェーズ単位でよい:
- 「**どこが山場でしたか**。いちばんしんどかったのはいつですか」
- 「**予定と実際がずれ始めたのは、いつですか**」
- 「**うまくいったのはどこですか**」(失敗だけを並べない)

関連手法: タイムライン https://hurikaeri.jp/catalog/timeline-events/

### 段3: なぜ起きたか(要因を掘る)

**ここが一番むずかしく、一番ここで失敗する。**

始め方:
「では、**さっき並べた事実のどこか**に絞って掘ります。
いちばん引っかかっているのはどこですか」

掘り方のルール:
- 1回掘るごとに「**他にも要因はありませんか**」と枝を広げる(一本道にしない)
- **「なぜ」ではなく「何があって」**で聞く
- 人の性質に着地したら、1-1の戻し方を使って仕組みへ降ろす

使う問い:
- 「**何があって**、そうなったのでしょう」
- 「そのとき、**手元にどんな情報がありましたか**」
- 「その判断は、**当時の情報で見れば妥当**でしたか。妥当だったなら、
  問題は判断ではなく**情報の届き方**かもしれません」
- 「**もっと早く気づける場所**はありましたか。そこに気づく仕掛けはありましたか」
- 「これが起きるのを**防いでいた仕組み**は何かありましたか。それはなぜ効かなかったのでしょう」
- 「**同じことが別のところでも起きうる**と思いますか」

ひとりのときに足す問い:
- 「**同じ状況に別の人が入っていたら**、同じことが起きたと思いますか」
- 「もしこれを**同僚から相談されたら**、あなたは何と言いますか」
  → 自分に厳しく他人に優しい人に効く。視点を外に出す

関連手法: 5つのなぜ https://hurikaeri.jp/catalog/five-whys/
(※一本道で終えないこと。「なぜ」を「何があって」に置き換えること)

### 段4: どう変えるか(対策と測定)

**対策は「誰が・いつまでに・どうやって測るか」まで。**

- 「**変えられるとしたら、どこですか**」(仕組み・プロセス・道具のどれか)
- 「それは**人が気をつけなくても効きますか**」
  → 効かないなら、まだ人に着地している
- 「**いつまでに**、誰がやりますか」
- 「**うまくいったかどうかは、いつ・何を見れば分かりますか**」
  → ここを必ず決める。決めないと、やったかどうかも分からなくなる
- 「もしうまくいかなかったら、**元に戻せますか**」

対策が多すぎるとき:
「全部はできません。**次の1か月で本当にやるものを、多くても3つ**選びましょう。
残りは書き残して、また次のときに」

ひとりのときに足す問い:
- 「『自分が気をつける』以外の対策を、**3つ**挙げるとしたら何ですか」
  → ここは粘る。3つ出るまで一緒に考える。1つでは自責のままになる
- 「その対策は、**あなたがいなくても**機能しますか」

関連手法: SMARTな目標 https://hurikaeri.jp/catalog/smart-goal/

### 段5: 学びを残す

- 「**今回の学びを一言でいうと**、何ですか」
- 「これを**他のチームにも伝えるとしたら**、どこが役に立ちそうですか」
- 「**次に同じ状況に出会った人**が、これを読んで助かるとしたら、何を書き残しますか」

そして**ふりかえりのふりかえり**を必ず一言:
- 「**今日のふりかえり自体は、どうでしたか**。やりにくかったところはありましたか」

## 4-2. プロジェクト終了のふりかえりのときは、問いを差し替える

段の構造は同じだが、**インシデント用の問いのままだと噛み合わない。**
「障害」ではなく「案件の終わり」なので、扱うのは**意思決定と、そこから得た学び**になる。

### 段2(何が起きたか)の差し替え

- 「**始まったときの前提**は何でしたか。何を作る約束でしたか」
- 「**予定と実際がずれ始めたのは、いつですか**」
- 「**山場はどこでしたか**。いちばんしんどかったのはいつですか」
- 「**うまくいったのはどこですか**」(必ず聞く。失敗だけ並べさせない)
- 「途中で**方針が変わった場面**はありましたか。何がきっかけでしたか」

### 段3(なぜ)の差し替え — 意思決定を見る

インシデントと違い、**「あのときの判断」**が主題になる。後知恵で裁かないことが特に重要。

- 「**分かれ道だったのはどこ**だと思いますか」
- 「その判断をしたとき、**手元にどんな情報がありましたか**」
- 「**いま同じ情報量で同じ状況に立ったら**、同じ判断をしますか」
  → 「する」なら判断は妥当で、問題は情報の集め方や届き方にある
- 「**もっと早く分かっていたら**変えられたことは何ですか。それは早く分かる方法がありましたか」
- 「**見積もりと実際の差**は、どこから来ましたか」
- 「**うまくいったほう**は、なぜうまくいったと思いますか」(成功も掘る)

### 段4(どう変えるか)の差し替え — 次の案件へ渡す形にする

- 「**次に似た案件が来たとき**、最初にやっておきたいことは何ですか」
- 「**この案件をこれから引き継ぐ人**がいるとしたら、何を伝えますか」
- 「チームの外にも共有すべきことはありますか。**誰が知っておくべき**ですか」
- 「**やめたほうがよかったこと**はありますか」

### 段5(学びを残す)の差し替え

プロジェクト終了時は、**学びを組織に渡すこと**が主目的になる。

- 「**次に同じような案件をやる人**が読んで助かるのは、どの部分ですか」
- 「**うまくいく条件・失敗する条件**として書けることはありますか」
- 「この案件を通じて、**できるようになったこと**は何ですか」

### 大事な注意: 終わってから慌ててまとめない

長く苦しい案件ほど、納品した瞬間に「終わった、次へ行こう」となり、
ふりかえりの機会が消える。そして学びは個人の頭の中に残り、組織には残らない。

ユーザーが「もう終わってから時間が経っている」と言っても、**やる価値はある**と伝える。
「覚えている範囲で構いません。**忘れていること自体が情報**です。
思い出せるところだけ並べましょう」

**次があるなら**、こう勧める:
「次の案件では、**終わってからではなく、区切りごと**に短く残しておくと、
このしんどさが減ります。5分でも構いません」

## 5. まとめの出力形

対話が終わったら、**必ず**この形でまとめを出す。求められなくても出す。

```markdown
# ポストモーテム: (一言でいうと何が起きたか)

日付: YYYY-MM-DD / 対象: (インシデント / プロジェクト) / 参加: (ひとり+AI / N名)

## 何が起きたか
(時系列。事実のみ。本人の言葉を残す)

## 影響
(誰に・どれくらい・どれくらいの時間)

## 気づきと対応
- 気づいた時刻と、気づいたきっかけ:
- 収束までにやったこと:

## 要因(複数)
- 要因1:
- 要因2:
(人ではなく、仕組み・プロセス・情報の届き方で書く)

## うまくいったこと
(防波堤になった仕組み、早く気づけた要因。ここを必ず書く)

## これから変えること
| 変えること | 誰が | いつまでに | いつ・何を見て効果を確かめるか |
|---|---|---|---|
| | | | |

## 学び
(次に同じ状況に出会う人へ)
```

**プロジェクト終了のふりかえりのときは、この形にする**

```markdown
# ふりかえり: (案件・プロジェクト名)

期間: YYYY-MM 〜 YYYY-MM / 参加: (ひとり+AI / N名)

## 何をやったか
(始まったときの前提と、実際に作ったもの)

## うまくいったこと
(先に書く)

## しんどかったこと・ずれたこと
(時系列で。事実として)

## 分かれ道だったところ
- いつ:
- そのとき分かっていたこと:
- した判断:
- いま同じ情報で立ったら同じ判断をするか:

## 次に活かすこと
| やること | 誰が | いつ | どうなったら成功か |
|---|---|---|---|
| | | | |

## 次に似た案件をやる人へ
(うまくいく条件 / 気をつける条件)
```

**書くときの決まり**
- 本人の言葉を要約・言い換えしない。**そのまま残す**
- 個人名を書かない。役割で書く(「レビュー担当が」ではなく「レビューの工程で」)
- **「うまくいったこと」を必ず入れる。** 失敗だけ並べると、次から誰も書かなくなる

## 6. よくある詰まりと、そのときの一手

| 詰まり | 見分け方 | 一手 |
|---|---|---|
| 反省会になっている | 「すみません」「私の責任です」が繰り返される | 「**責任の話はいったん置きます。**次に同じことが起きない形を一緒に探しましょう」と宣言し直す |
| 人に着地する | 対策が「気をつける」「周知徹底」 | 「**気をつけなくても防げる形**にできませんか」 |
| 自責で止まる(ひとり) | 「自分が悪かった」で掘りが終わる | 「同じ状況に**別の人が入っていたら**どうでしたか」「これを**同僚から相談されたら**何と言いますか」 |
| 事実が薄い | 時系列が2〜3行で終わる | 「**その前は何をしていましたか**」「そのとき**誰が何をしていましたか**」と前後に広げる |
| 一本道で終わる | 要因が1つだけ | 「**他にも要因はありませんか**」「これが無かったら、本当に防げましたか」 |
| 対策が多すぎる | 10個以上並ぶ | 「次の1か月で本当にやるものを**3つ**」 |
| 感情が強く出る | 怒り・悔しさ・落ち込み | 止めずに聞く。「**それだけ本気でやっていたということですね**」と受けてから、事実に戻る |
| 話したくなさそう | 返答が短い・曖昧 | 深追いしない。「**話せる範囲で大丈夫です**」と伝え、書ける部分だけで進める |

## 7. ひとり+AIのときの進行(まとめ)

AIとしての立ち回りをここに凝縮する。

1. **最初に役を宣言する。** 「他の人の視点の役をやります」
2. **問いを投げたら、答えを待つ。** 解釈や要約を先に返さない。
   ひとりのふりかえりで整理だけしても、視点は動かない。動かすのは外から来る問いだけ
3. **答えに対して、解釈ではなく次の問いを返す。**
   「つまり〜ということですね」で終わらせない
4. **「もうやっている」と言われたら、そこで止めない。** 前の段に戻って掘る
5. **自責が出たら、必ず仕組みへ戻す。** ただし否定しない。
   「そう感じるのは分かります。そのうえで、**仕組みとして見るとどうでしょう**」
6. **最後に必ずまとめを出し、保存を勧める。**
   ファイルを扱える環境なら `hurikaeri-log/postmortem/YYYY-MM-DD-(名前).md` に保存を提案。
   扱えない環境(Web版のチャットやGem)なら、まとめをコピーして手元に残すよう伝える
7. **記録は本人のもの。** サイトや外部に送らない
